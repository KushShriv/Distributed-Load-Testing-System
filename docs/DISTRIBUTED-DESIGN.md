# Optional distributed drivers: draft design

Status: design only. Remote drivers, this protocol, and the deployment flow do not exist in the local preview. Phase 3 implementation is gated on Phase 1–2 acceptance. All limits and protocol details below need validation before implementation.

## Topology and trust

A user operates one controller and one or more drivers on machines they control. Drivers initiate outbound connections to the controller over a private network or a user-managed VPN. The controller remains the only authority that starts and cancels tests. A separate browser-facing local API stays on loopback; it is not the driver protocol. Neither Kafka nor an unauthenticated control interface is exposed. There is no shared multi-user service.

Each driver connection uses TLS with mutual certificate authentication. The controller validates a driver certificate against a dedicated, user-controlled CA and an explicitly enrolled driver identity; each driver validates the controller certificate and expected DNS name. Enrollment is an explicit local administrative operation: create a driver identity and provision its certificate and key through a secure channel chosen by the user. Never put private keys, pairing codes, or enrollment secrets in URLs, logs, images, or source control. Store keys with restricted file access. Provide a way to revoke a lost driver certificate and disconnect that identity; rotation and revocation must be tested. A compromised enrolled driver can cause harm within its network and delegated allowance; TLS does not make an untrusted host safe.

The driver endpoint binds to a user-selected private interface and port, never all interfaces by default. Firewall rules allow the controller port only from enrolled drivers' known addresses; driver hosts need outbound access to the controller and to explicitly authorized test destinations. Apply least-privilege OS accounts and deny unrelated inbound traffic. Remote access requires an explicit configuration step and visible warning. A driver must not accept inbound run commands from arbitrary peers.

## Protocol outline

Use a versioned, authenticated, length-bounded control protocol over the encrypted connection. Exact wire format, compatibility rules, frame limits and retry intervals are implementation decisions, not promises. Every message carries a protocol version, controller-issued run ID, driver ID, message ID and sequence number as applicable. Reject unknown versions, invalid state transitions, replayed or duplicate commands, oversized messages and drivers outside the enrollment allowlist. Commands and result updates must be idempotent. Neither reconnect nor retry can create a second run or duplicate a counted result.

1. **Register:** After TLS authentication, the driver reports its version, configured capacity and capabilities. The controller binds the certificate identity to the registered driver, rejects duplicate active identities and admits only compatible drivers. A reconnect resumes only after the controller reconciles its last accepted sequence and current run state.
2. **Heartbeat:** Each driver periodically sends a bounded heartbeat with run state, claimed and completed attempts, error totals and remaining allowance. The controller uses its own monotonic clock to mark a missing heartbeat stale. Stale or disconnected drivers stop initiating requests when their short-lived local authorization expires. The controller shows their last confirmed state and never treats silence as success.
3. **Start:** The controller checks user authorization for the target and redirects, shows aggregate workers, request budget, duration, per-driver allocation, permitted private networks and rate before explicit confirmation. It sends a run specification with a unique ID, target and redirect policy, worker count, hard attempt budget, per-driver request rate and burst, duration and body/redirect/timeout limits. Each driver repeats URL validation and DNS/destination checks at each connection and redirect, including explicit private-network permission. Driver-local `localhost` refers to that driver, not the controller. Each worker has at most one in-flight request.
4. **Progress and final results:** Drivers send cumulative, sequence-numbered snapshots and a final report. A reconnect sends the latest cumulative state, not an additive replay; the controller replaces each driver's prior snapshot after validating sequence and monotonic counters. Persist or retain enough bounded run metadata for safe recovery; define restart behavior before implementation. Never reissue an uncertain request allowance after a disconnect or restart.
5. **Cancel:** The controller marks the run cancelling and sends an idempotent cancellation command to every participating driver. Drivers immediately stop starting requests and allow in-flight requests to finish or reach their timeouts, then acknowledge and report final counts. If a driver cannot be reached, the controller reports cancellation as unconfirmed until its local authorization expires; it does not label the whole run cancelled successfully before that condition is met.

## Aggregate limits and measurements

Before starting, allocate each driver's fixed request budget so their sum does not exceed the user-confirmed global maximum. An attempt consumes budget immediately before it starts. Do not reclaim or reassign unused or uncertain budget from a lost driver during the run: this can leave capacity unused but prevents a partition from exceeding the total. Apply the lower of per-driver and controller limits. Enforce maximum workers, duration, body bytes, redirects, connection/read timeouts, and attempt budget on both controller and drivers; no unbounded queue.

For rate limiting, assign each driver a token bucket whose refill rate and burst sum across drivers are at most the configured aggregate rate and burst. Driver buckets use local monotonic elapsed time and do not accumulate extra credit while disconnected. This bounds aggregate starts over an interval by the shared burst plus the aggregate refill allowance, subject to scheduler and measurement precision; it is not a promise of perfectly even requests each second. A disconnected or expired driver cannot start requests, and the controller must not allocate its rate to another driver until the prior authorization is known expired. Acknowledged grants may use a conservative expiry bound calculated from the controller’s receipt of the acknowledgement plus the grant lifetime and a documented clock-rate margin. If delivery or acknowledgement is uncertain, do not reallocate that rate during the run. This requires a tested bound on monotonic clock-rate error; without one, keep the allocation reserved. Define rounding, restart, clock anomalies and authorization expiry behavior in tests before release.

Drivers use their own monotonic clocks for request latency, local elapsed time and expiration; never subtract wall-clock timestamps from different hosts. Record final HTTP status counts, successes, transport errors and sampled or bounded mergeable latency histograms. Latency includes redirects and bounded response reads; HTTP response latencies include error statuses, while transport failures are separate. Merge compatible histograms and counters, not per-driver percentile values; report histogram precision with aggregate p50, p95 and p99. The controller can report total completed attempts divided by its own monotonic elapsed time from dispatch to the final accepted result, explicitly including coordination overhead. Per-driver rates use each driver's own elapsed time. Neither measure requires synchronized clocks.

The run is **complete** only after each admitted driver sends a valid final report. A driver with an error, expired authorization, missing final report or lost connection is listed individually with its last confirmed counts and reason. Aggregate only confirmed, deduplicated snapshots; label totals and percentiles partial where data is missing. Do not invent zero errors or present incomplete data as a successful full run. JSON/CSV exports include per-driver status, allocations, time bases, histogram precision and completeness.

## Deployment, cost, and cleanup

The user provisions and controls the machines, certificates, private network/VPN, firewall rules and target access. An EC2 deployment may incur instance, storage, network transfer, public IPv4, NAT gateway, VPN and other service charges; actual cost depends on configuration, region, duration and current provider pricing. Estimate and approve costs before provisioning. The local launcher must not create cloud resources or request AWS keys.

A future deployment guide must include platform prerequisites; exact controller and driver commands; private bind addresses; certificate issuance, rotation and revocation; firewall and egress rules; preflight checks; stop and restart procedures; and a resource inventory. On shutdown, cancel runs, stop services, revoke or remove driver credentials, close firewall rules, and remove temporary files and user-created cloud resources as appropriate. Confirm destructive deletion of user resources. The guide must explain how to check that billable resources have stopped.

## Decisions and verification before implementation

- Measure a simple direct controller–driver transport first. Introduce Kafka only if a measured requirement justifies its operational and security cost; the original prototype is not evidence of that need.
- Choose the wire format, certificate provisioning method, per-driver authorization lifetime, histogram format, capacity defaults and persistence/restart model. Document the failure and cost tradeoffs.
- Test certificate rejection and revocation, unauthorized enrollment, replay, duplicate messages, malformed frames, reconnects, stale heartbeats, partitions, expired grants, restart recovery, cancellation with in-flight requests, redirect revalidation, rate and attempt limits, partial results, and aggregation without synchronized clocks. Use controlled user-owned fixtures only.
